# Repository maintenance guidance

Generative Web Guard is a prototype security boundary for generated HTML, SVG,
and JavaScript. Keep claims tied to the boundary actually implemented and
tested. The browser demos and CDN entry points run the Lean checker compiled to
WebAssembly as the acceptance authority; the JS checker still runs as a
candidate builder and its candidate must match Lean's accepted tree exactly.
That is not a proof of JS equivalence, and everything around the checker --
parsing, the JSON codec, the C shim, the trusted glue, the renderer, the
browser -- remains outside the theorems.

## Repository skills

These skills live in the repository so contributors share the same guidance.
Read the relevant `SKILL.md` when doing the indicated work; paths are relative
to the repository root. They need not be installed in a user's global skills.

- [guard-policy-maintenance](skills/guard-policy-maintenance/SKILL.md): policy,
  validator, Lean-proof, and exploit-regression changes.
- [guard-distribution](skills/guard-distribution/SKILL.md): generated bundles,
  package entry points, CDN releases, and build CI.

For other tasks, use the maintained documentation as needed:
[verification](docs/VERIFICATION.md), [red-team intake](docs/RED_TEAMING.md),
and [security FAQ](docs/faq.md).

## Source ownership

- `rules/policy.json` owns policy tables, validator selections, parameters, and
  limits. `rules/capabilities.json` is the reviewed capability kernel that
  bounds every profile; widening it is a kernel change, not a profile edit.
  `rules/catalog.json` owns rule identities and evidence links.
- Custom algorithms live separately in `src/policy.js` and
  `lean/Guard/Validators/`; traversal and acceptance also have two implementations.
- Regenerate tables with `npm run gen:policy` and rule IDs with
  `npm run gen:rules`. Edit their sources, not generated output.
  `src/policy-data.js`, `src/capabilities-data.js`, `src/rules.js`,
  `lean/Guard/Core/Limits.lean`, `lean/Guard/Rules.lean` and
  `lean/Guard/Policy/{Capabilities,Tables/*}.lean` are all generated.
- parse5 is the single production HTML frontend: `src/cdn.js`, both demos and
  the policy Worker use `src/adapters/parse5.js`. `src/adapters/dom.js` is kept
  only for explicit parser-differential compatibility tests.
  Parser behavior must be assessed separately from raw-tree validation.
- Preprocessing limits live in `src/policy-protocol.js` and bound input work
  before the policy runs; `src/gate.js` is an optional development linter, not
  a security boundary, and ships from `src/cdn-lint.js`. `maxRawPathNodes`
  there -- raw nodes open at once in a depth-first walk -- is a MEASURED
  per-engine bound on the Lean checker's per-sibling recursion, not a round
  number, and `maxRawNodes` is capacity: re-measure with
  `scripts/wasm-audit.mjs` and the browser check before changing either
  (docs/csp.md).
- The Lean/Wasm acceptance authority is `src/lean-abi.js` (wire contract),
  `src/lean-checker.js` (one sealed instance, poisons on a trap, never falls
  back), `src/lean-module.js` (the embedded binary) and `src/acceptance.js`
  (one-time records binding a verdict to a frame commit). `lean/Guard/Io/Abi.lean`
  and `lean/Guard/Io/Decode.lean` are the Lean halves; `lean/Guard/Io/Api.lean`
  is the batch interface and is deliberately NOT exported from the Wasm build.
  `dist/lean-checker-wasm.js` and `cdn/asset-manifest.json` are generated by
  `scripts/build.mjs`. Adding any fallback to JS acceptance would defeat the
  whole arrangement; a failure must refuse to render.
- `scripts/build.mjs` generates committed `cdn/` and ignored `dist/` files.
  `node_modules/`, `lean/.lake/`, and `lean/wasm/dist/` are local build outputs.
  Keep `generated-page-security-plan.docx` local and ignored.

## Verification and handoff

Choose checks proportional to the change. Documentation-only edits need link
and whitespace checks, not a full toolchain rebuild. Policy/proof changes need
the full verification path; rendering and Worker changes need browser evidence.

- `npm run test:js` is explicitly JS-only; its Lean skip is intentional.
- `npm test` requires Docker toolchain images, builds current Lean and Wasm,
  audits proofs, and checks behavior across all engines. Use
  `npm run setup:verification` to prepare missing images.
- `npm run build` and `npm run check:cdn` verify the distribution separately.
- For browser checks, serve on an available port and set `DEMO_URL` explicitly:
  `PORT=8089 npm run serve`, then
  `DEMO_URL=http://localhost:8089/ npm run check:browser`.
- `.github/workflows/build.yml` runs the browser/CDN job plus an unconditional
  `proofs-and-full-verification` job that builds the pinned toolchains, runs
  full `npm test` from the checkout, and fails on missing toolchains or stale
  generated files. Report exactly which checks ran and any skips.

Use Conventional Commit subjects when commits are requested. Prefer coherent
whole-file groups for runtime, Lean, build, and advisory tooling; do not split
files into staged hunks just to manufacture those groups. Creating a local
change does not by itself authorize publishing packages or pushing a release.

The advisory scout writes GitHub issues unless `SCOUT_DRY_RUN=1` is set.
Use dry-run mode for local report inspection. Its bounded keyword search is an
intake aid, not comprehensive CVE coverage or an automatic policy updater.
